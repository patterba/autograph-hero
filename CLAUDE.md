# Notes for Claude

- Static site, zero dependencies. `node build.mjs` writes `dist/`. Do not add a framework or npm packages without asking.
- Data comes from Supabase project `ravavlocylqvkmthevtv`: `public.signings` (rows with status 'published') and `public.athletes` (each signer's pro teams from Wikipedia, rows with status 'confirmed'). The weekly crawl scheduled task fills both. Team names feed search and the cards.
- Photos: the promoter's photo (signings.image_url) comes first; the player's free Wikimedia Commons photo (athletes.image_url) is the backup, also swapped in by the browser if the promoter photo fails. Commons photos are credited on the signing page and on /photo-credits/. The Supabase function `athlete-photos` finds them; the workflow calls it before each build.
- All text from the database is scraped from other websites: always pass it through `esc()` and URLs through `safeUrl()`.
- Internal links go through `link()` so the site works in a sub-folder (e.g. /new on Bluehost) and at the domain root.
- Hosting is Bluehost (Apache). The workflow uploads over FTP; the build writes an .htaccess.
- Design tokens are CSS variables at the top of `assets/site.css`.
- Forms: "Submit a signing" (/add/) and "Sign Up" (/signup/) post to the Supabase function `site-forms` (assets/forms.js). Listings land in `public.submissions` as pending; `admin.approve_submission(id, note)` / `admin.reject_submission(id, note)` decide them (the private approval artifact calls these). Sign-ups land in `public.subscribers`; every sign-up gets a confirmation email (with up to 4 soonest upcoming signings that match the fan's favorites by signer or team, each with photo and link to its signing page) from site-forms via Resend (welcome for new, "updated" for repeat; sender MAIL_FROM, default alerts@autographhero.com). The Resend key is read from the RESEND_API_KEY function secret, else from Vault secret 'resend_api_key' via public.site_resend_key() (service role only). Resend domain autographhero.com uses CNAMEs send/rsend at Bluehost DNS. Both tables are private (RLS, no policies). The site rebuilds hourly.
- Captcha: Cloudflare Turnstile on /add/ and /signup/ (`captchaBox()` in build.mjs). Site key built into build.mjs (0x4AAAAAAFqb9fLxUdjBVuqy, widget "Autograph Hero" in the owner's Cloudflare account; env TURNSTILE_SITE_KEY overrides) and also on /contact/; site-forms and signing-reminders verify with the secret: the TURNSTILE_SECRET_KEY function secret if set, else Vault 'turnstile_secret_key' (read with `public.site_turnstile_secret()`, service role, re-read every minute). The owner saves it on the admin page's Captcha tab (`public.admin_set_turnstile(secret)`, '' = off; `admin_turnstile_on()`). The owner's project lives in a second Supabase account; secrets saved in the other account never reached it. Since 2026-10-28 TURNSTILE_SECRET_KEY is also set as a function secret in the right account (same value as Vault, checked); RESEND_API_KEY is still Vault-only. No secret = no check.
- Members: email + password accounts (Supabase Auth). /signup/ takes a password; site-forms creates the login already confirmed (`email_confirm: true`, no confirmation email) and replies `login: true`, then assets/forms.js signs in with the password grant and opens /account/?welcome=1. An existing login's password is never changed by Sign Up. /account/ (assets/account.js): password login, "Forgot password?" → site-forms `form: "reset"` emails (Resend) a link `/account/?verify=<token_hash>&type=recovery`, which the page exchanges via POST /auth/v1/verify and then shows "Set a new password"; change password while logged in (PUT /auth/v1/user). Session kept in localStorage 'ah-session'. Logged in, /account/ has two tabs: "Your Feed" (default; every upcoming signing card is built into the page hidden with data-terms = signer names + their teams, and account.js shows the ones matching the member's favorites with the same rule as the emails) and "Change Preferences" (details, favorites, alerts, password, delete). Members read/edit their own row via `public.my_account()` / `public.update_my_account(name, favorites, alerts)` (security definer, matched on the JWT email); site-forms `form: "delete_account"` deletes the row and the login (refuses admin logins). `public.site_auth_user_exists(email)` is service-role only. The older emailed-login-link route (`form: "login"`) still exists but isn't used by the site.
- Terms (/terms/) and Privacy (/privacy/) are written in build.mjs (`termsPage`, `privacyPage`); bump POLICY_DATE when editing. Contact email comes from the GitHub variable CONTACT_EMAIL.
- Analytics: Cloudflare Web Analytics; the token is built into build.mjs (public), the GitHub variable CF_ANALYTICS_TOKEN can override it, ANALYTICS=off builds without it (no cookies, so no banner). Mention any new tracking in the privacy page.
- The build's .htaccess redirects old WordPress addresses (/terms-conditions/, /privacy-policy/, /my-account/, /submit-an-appearance/, /type/, /browse/).
- Admin: /admin/ (assets/admin.js), not linked, noindex, disallowed in robots.txt. Email + password login (Supabase Auth); only logins with app_metadata.role = 'admin' can call `public.admin_queue()` and `public.admin_decide(id, approve, note)` (which wrap admin.approve_submission / reject_submission). The owner's admin login is patterba@hotmail.com (created 2026-10-25). To add another admin, create the user in the Supabase dashboard and set app_metadata {"role":"admin"} with the service role. The edge function `admin-setup` is a disabled stub (returns 410).
- The site is live at the domain root since 2026-10-25 (FTP account deploy@ → /home1/bhiwyfmy/public_html, which also still holds the old WordPress files). Cloudflare sits in front of the domain; purge its cache if visitors see stale pages. Each publish writes a report to the `deploy-check` branch (what Bluehost serves directly vs through Cloudflare).
- The site-forms function's source is kept in `supabase/functions/site-forms/index.ts` (deployed with the Supabase MCP `deploy_edge_function`, verify_jwt false). Keep the copy in the repo in sync when you change it; its `slugify`/`joinNames` must match build.mjs so email links hit real signing pages.
- Weekly alerts: edge function `weekly-alerts` (source in `supabase/functions/weekly-alerts/index.ts`, verify_jwt false, checks header x-cron-secret = Vault 'weekly_alerts_secret' via public.site_cron_secret()). pg_cron job 'weekly-alerts' runs Fridays 17:00 UTC and calls it with pg_net. It emails each active subscriber whose favorites match signings published since their `last_digest_at` (max 8 days back; `signings.published_at` is set by a trigger when status becomes 'published'): "New this week" cards (max 8) then "Also coming up" (max 4), via Resend batch. Test with POST {"only": email, "force": true} or {"dry": true}. {"roundup": N} also emails fans with nothing new their next N matches ("Coming up for your favorites", used 2026-10-30); {"only": email, "copy_to": you} sends you a copy of that fan's email (unsubscribe link disabled, their record untouched). Every alert email links to /unsubscribe/?t=<unsubscribe_token>; the page's button posts site-forms `form: "unsubscribe"`.
- Email logo: `assets/email-logo.png` (rendered from the header SVG with the Yellowtail font; email apps don't show SVG). Emails load it from raw.githubusercontent.com/patterba/autograph-hero/main/assets/email-logo.png, not autographhero.com, because Cloudflare's bot check can block email image proxies. Re-render it if the logo changes.
- SEO: page() writes canonical, Open Graph/Twitter tags (share image `assets/social.png`, 1200x630, rendered like the email logo; re-render if the logo changes) and JSON-LD passed as `ld`. Home: WebSite (+ SearchAction to /events/?q=) and Organization. Signing pages: titles/descriptions from `signingMeta()`, BreadcrumbList, and schema.org Event (`eventLd()`, in-person signings with a date and place only). Hub pages: /autographs/<slug>/ (one per signer, from athletes + signings), /teams/<slug>/, /sports/<slug>/, plus A–Z lists /autographs/ and /teams/ (`buildHubs()`); slugs are `slugify(name)`. Hubs with no upcoming signings still exist but are `noindex, follow` and left out of the sitemap. /account/ is noindex. Search Console / Bing ownership tags come from GitHub variables GOOGLE_SITE_VERIFICATION / BING_SITE_VERIFICATION (home page only). Google Search Console is verified with the HTML file /google9017fd775e03a772.html, which the build writes; keep it.
- Admin Analytics tab (assets/admin.js `loadAnalytics`): "Visitors" from Cloudflare Web Analytics through the edge function `admin-analytics` (source in `supabase/functions/admin-analytics/index.ts`, verify_jwt false, checks the caller is an admin via /auth/v1/user; GraphQL `rumPageloadEventsAdaptiveGroups`, picks the siteTag(s) whose requestHost is autographhero.com). The Cloudflare API token (Account Analytics: Read) is pasted on the tab and saved to Vault ('cf_analytics_token', optional 'cf_account_id') by `public.admin_set_cloudflare(token, account)`; `admin_clear_cloudflare()` blanks it; the function reads it with `public.site_cf_settings()` (service role; empty = not connected). Unique visitors are our own cookie-free count: every page (not admin) calls `navigator.sendBeacon` to the edge function `site-visit` (source in `supabase/functions/site-visit/index.ts`, verify_jwt false; skips bots and other sites), which calls `public.site_record_visit(ip, ua)` (service role): sha256(daily random salt in private.visit_salts + IP + UA) stored once per day in `public.site_visitors` (old salts deleted). The tab reads `public.admin_unique_visitors(days)` and sums the days. VISIT_COUNT=off builds without the beacon. It's described on the privacy page. (autographhero.com isn't a zone in the owner's Cloudflare account, so Cloudflare's own unique count isn't available.) "Members" and "Signings" come from `public.admin_stats()` (admin only). A locked test login analytics-test@autographhero.invalid (banned, no role) is left over from testing; it can be deleted in the dashboard.
- Signing Archives (/archive/, `archivePage()`, footer link): past signings, newest first by month. The weekly crawl marks old rows status 'past'; `signings.was_listed` (set by the signings_published_at trigger whenever a row is published) plus the RLS policy "Public can read past listed signings" let the site read past rows that were once on the site. The build loads status in (published, past); `s.past` = status 'past' or date gone by. Past signings keep their /signing/ pages (notice, no order/calendar/map buttons, no Event data) and show under "Past signings" on signer and team pages.
- Installable app (PWA): build.mjs writes `manifest.webmanifest`, `sw.js` (`serviceWorker()`: network-first pages with offline copies, cache-first /assets/ and Google Fonts, never /admin/, `/offline/` fallback, push + notificationclick handlers for future alerts) and `/offline/`; `appHead()` adds theme-color, manifest, apple-touch-icon, apple-mobile-web-app-* and 15 portrait `apple-touch-startup-image` links (not on /admin/). `assets/app.js` (every page but admin) registers the worker and turns the phone bottom bar (`.submit-bar`, which slides up once the header scrolls away) into an install prompt instead of "Submit A Signing" when the app can be installed (iOS Safari: "How to install" expands the Add to Home Screen steps; Android: `beforeinstallprompt` Install button). It stays the submit bar inside the installed app, in in-app browsers, on /app/ /add/ /signup/ /offline/ /unsubscribe/ /reminder/, and for 14 days after someone closes the install prompt. It also fills `[data-app-panel]` on /app/ ("Get the App", footer link, in the sitemap). Icons and launch screens in `assets/app/` are rendered from the caped H in assets/logo.svg (orange #FF6A00 tile; maskable ones keep the mark in the 80% safe zone); re-render if the logo changes. The .htaccess serves .webmanifest as application/manifest+json and sw.js with no-store.
- Reminders: "Email me a reminder" on upcoming signing pages (`remindBox()`, shown when `remindable(s)`; `assets/remind.js`). Members send their login token from localStorage 'ah-session' (refreshed if expired); others send an email (honeypot, min 1.5 s on page, 12/hour per visitor hash, Turnstile when TURNSTILE_SITE_KEY / TURNSTILE_SECRET_KEY are set). Everything server-side is the edge function `signing-reminders` (source in `supabase/functions/signing-reminders/index.ts`, verify_jwt false; deployed with the Supabase MCP): public POST {form:"remind"} saves to `public.reminders` (private: RLS, no policies; unique email+signing; `cancel_token`) and emails a confirmation with `/reminder/?cancel=<token>` (`reminderPage()`), {form:"cancel_reminder"} deletes it; with header x-cron-secret (Vault 'weekly_alerts_secret') it's the hourly sender: pg_cron job 'signing-reminders' at :07 sends due reminders via Resend batch, marks 'sent'/'missed', deletes done rows after 30 days. Timing (`plan()`): in person = parsed start time (event_time_text, zone from state or a PT/ET hint) minus 24 h, else 9 AM local the day before; mail-in/private = 9 AM Pacific the day before order_deadline (no reminder once it's passed). Test with {"dry": true} or {"only": email, "force": true}; use delivered@resend.dev for test sends. A trigger on public.subscribers deletes an account's reminders. The .ics files carry a VALARM (TRIGGER -PT15H = 9 AM the day before). Described on the privacy page.
- About (/about/, `aboutPage()`) and Contact (/contact/, `contactPage()`), both linked in the footer, which also has a short "About Autograph Hero" blurb. The About copy is written in the owner's voice without personal specifics (name, history); add them if the owner provides them. The contact form (data-form="contact" in assets/forms.js) posts site-forms `form: "contact"`: saved to `public.contact_messages` (private: RLS, no policies; `emailed` flag) and emailed via Resend to CONTACT_TO (function env, default autographhero@gmail.com) with Reply-To = the sender; 5/hour per visitor, honeypot, min fill time, Turnstile when set. Described on the privacy page.
- Header nav has "Advertise With Us" (just "Advertise" under 1180px) → /contact/?topic=advertise; assets/forms.js preselects the matching topic from ?topic=. Ad placements on the site are a planned next step.
- Names: Sign Up and the account page ask for First name and Last name (both required, no one-word names). They are stored together in `subscribers.name` ("First Last"); account.js splits on the first space. site-forms rejects a missing first/last name (or, from an old cached page sending only `name`, a one-word name), and `update_my_account` rejects a name without a space. Members who signed up before 2026-10-30 with one word must add a last name the next time they save their details.
